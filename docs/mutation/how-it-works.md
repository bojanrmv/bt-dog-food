# How it works

[Mutation testing](README.md) › How it works

1. **Sandbox.** A folder in `%TEMP%/dgf-mutate`, named after the repository and a hash of its path. Every worktree of a repository uses the same sandboxes (dgf asks git for the main checkout), so the first run in a new worktree brings a built sandbox up to date instead of building everything; a file whose size matches but whose time differs (a fresh checkout) is compared by content and left alone when it is the same, so the build stays incremental. It holds only what the tests need: for C#, the chosen test projects and every project they reference (each project folder without `bin` and `obj`), the files in every folder above them up to the repository root (where `Directory.Build.props`, `Directory.Packages.props`, `global.json` and `NuGet.config` live) with any `.config` folder there, and files that project, `.props` and `.targets` files import or include from elsewhere (`..\build\Shared.props`). For TypeScript and JavaScript, the package folder with the test runner, and the files above it. `sandbox = "full"` copies the whole repository instead, and dgf does that by itself, with a note, when the smaller copy does not build.

   The sandbox is kept between runs and brought up to date file by file: new and changed files are copied, deleted ones removed, and the build output stays, so the next build only compiles what changed. Links and NTFS junctions in the repository, and every `node_modules` folder, are linked again in the sandbox, never copied; removing the sandbox removes the links, not what they point at. A run locks its sandbox; a second run at the same time takes the next one (`-2`, `-3`, ...).

   With the default `--min-complexity`, the code outside functions is chosen too: module-level constants and tables, property and field defaults, base-constructor arguments. Decorators, attributes, enums and other compile-time constants stay out. These mutants show as `(outside functions)` and are scored apart, so a function's score and the exit code say nothing about them. Any change to the file tests them again.

   Only the files with chosen functions are rewritten. Every mutated expression becomes a switch, nested where expressions nest: `a > b` turns into `(DgfMutants.Is(17) ? (a >= b) : (a > b))`. Every line keeps its number: line breaks in the mutated copy become spaces, or, in C# when the copy holds a string spanning lines or an `#if`, stay between `#line` directives. C# gets a small `DgfMutants.g.cs` in each mutated project; TypeScript and JavaScript get a `__dgfIs` function appended at the end of the file (function declarations are hoisted, so no line moves). In TypeScript a switch keeps the original's type, so the tests type-check, and Angular templates are checked, against the code as written: the mutated arm of an expression is `(mutated) as never`, and the mutated arm of a statement that ends a function's body (emptying it, say) ends with `return undefined as never;`, so the function's inferred return type does not gain `undefined`.
2. **One build.** C#: `dotnet build` of a solution with the chosen test projects, with analyzers off (source generators still run), warnings not treated as errors, and no NuGet audit: these slow a build down or fail it for reasons that have nothing to do with the mutants. Angular: `tsc --noEmit` on the spec tsconfig. Vitest and Jest need no build: they strip types on load.

   Mutants that do not compile (for example `+` on a `DateTime`, or `&&` → `||` that breaks TypeScript's narrowing) are found from the compiler's error lines. A mutant on an error's line is marked *did not compile* and removed. An error on a line with several mutants, or with none, makes them, or every mutant of that function, suspects: they are taken out together and put back half at a time until the culprit is found, so the others are still tested. Errors that point at a use or at the end of a function rather than at their cause (C# "use of unassigned local variable", "not all code paths return a value", TypeScript "used before being assigned") always make the whole function suspect. Suspects of different functions are searched for side by side, in the same builds. After the first build, only the projects with mutants are rebuilt (`--no-dependencies`: what they reference was built a moment ago) until they compile; a last build of everything the tests need follows. `--build-jobs N` (or `build_jobs`) passes `-m:N` to every build, and `--low-priority` runs dgf and everything it starts below normal priority (MSBuild's reused build nodes get `-lowPriority`). In C#, after the first build fails, that search runs on compile checks in memory (the C# engine `dgf-dup-cs`, which ships with dgf): each check takes a fraction of a second where a build takes seconds, so one more build confirms what it found. It runs no source generators, so an error counts only in a member that had no error like it without mutants: it can miss an error, which the builds that follow then find, but never adds one. Without the engine, or with an older one, the builds do the search as before, and the run says so in a note naming the engine it found.

   An error that names no mutant takes every mutant out for one build of everything the tests need. If that build still fails, the code does not compile without mutants. In a sandbox with only the tested projects, dgf then copies the whole repository (step 1). In a full one, a C# test project that is all that fails is left out, with a note giving its first error, and the other test projects run. dgf tells which ones fail from the project MSBuild names at the end of each error line, or by building each test project on its own when the errors name another project. Only when the projects with mutants fail, or every test project does, does the run stop with the errors. If the build without mutants passes but the error comes back once they go back in by function (a type that changes in one function and fails in another, or in a test project), half of the mutants still out go back per build: a clean build clears that half, and the error narrows the search to it, so each culprit costs a few builds. A file with mutants that is in no project folder (one that test projects link in) is compiled only by a build of the test projects, so its rounds build those. A build that finds a project's restore output missing (`NETSDK1004`) restores and builds again, whatever the sandbox's record of its last restore says.
3. **Reach, per test.** One test run with no mutant active and recording on; for C#, the test projects run side by side and share `--jobs` places. A test project is split into batches of whole classes, balanced by each class's time in the last run (class fixtures included), and its workers take the next batch when they are free, so a place a small project has finished with goes to a big one; a project gets another worker per 20 seconds of tests, and the workers stay warm for the mutants. Workers run with a larger first GC generation, no background GC and no profile-guided recompiling, unless the environment sets those. Every `Is(id)` call writes "test, mutant" once. A switch reached in code that runs once per process (a static constructor, which field initializers are part of; a lazy cache's factory; EF Core's `OnModelCreating`) writes the kind too: in .NET the switch reads the stack on a test's first hit of a mutant and again at its 2nd, 4th, 8th ... 1024th, so a site reached from ordinary code first and from a static constructor later in the same test is still found, at a bounded cost. A static constructor's mutant is *outside any test* whatever tests it is first seen in, even a helper that several classes' constructors call, each first touched in another test; it gets a process of its own (step 5). A lazy fill seen in two tests of one process runs for each test (a cache per test object) and belongs to those tests. The switch knows the running test: in .NET from AppDomain data `DgfTest`, which dog-food's test worker sets around each test, and for NUnit from NUnit's own `TestContext`, since NUnit's adapter reports a test's start at another moment than the test runs; in Node from `expect.getState().currentTestName`. Mutants no test reaches are *no tests* without running anything.

   Code reached inside a static constructor, a lazy cache's factory or EF Core's `OnModelCreating` runs once and serves every test after it, so its mutants are *reached outside any test* and run with every test (step 5). The switch notes the test such code ran in: a static constructor runs once per test process, so code found this way in two tests of one test project runs for each test (a cache per test object, such as a service built per test) and belongs to those tests instead.

   **Which mutants can change a value.** For a comparison whose operands have no side effects (`a.Count > limit`, but no call, indexer, assignment or `await`) and for an `if` condition that becomes `false`, the C# switch also works out what the mutants would give, in this run only: `(Probing ? Check(original, id, mutated, ...) : original)` evaluates the original once and each mutated copy next to it. Never inside a lambda or a query, which may be an expression tree a query provider translates. A mutant whose value never differed from the original's in any test that reaches it behaves the same in all of them: it *survives* without a run, and the report says no test changes its value and what input would (for a boundary, the two sides equal). One whose value differed in some tests runs with those only, since only they can notice it.

   **dog-food's test worker (C#).** dgf starts one worker process per test project, on the test project's own runtime and dependencies (its runtimeconfig and deps.json), and keeps it running: it loads the VSTest adapter next to the tests (xUnit, NUnit and MSTest each ship one) and finds the tests once, then serves every test run of the session. A test run costs its tests, not a test host's start, discovery, loading and compiling: on a real test project, 10 to 70 ms instead of 4 to 9 s. The plan of each run goes to the switches through AppDomain data. A Microsoft.Testing.Platform test application (xUnit v3, the MSTest runner, TUnit) runs in the platform's server mode instead, kept running the same way; it has no collector to say which test runs, so dgf asks for one test at a time and tells the switches the test and its mutant through a small mapped file. A worker serves one run at a time, so `--jobs` workers per test project run side by side. A project with several target frameworks runs on the newest one this machine has a runtime for, with a note. The workers are the only way tests run: a test project they cannot serve (.NET Framework, no VSTest adapter and not a test application) is skipped, with a note that names it and why, and the other test projects run; only when none can be served does the run stop. A mutant no test that ran reaches, in code a skipped test project uses through its project references, is reported as not tested rather than as having no tests, and is not cached, so the next run tests it. A worker that does not start is tried once more; if it still does not start, the first test run stops with the reason, and a later run's mutants are reported as not tested.
4. **Packing.** A test run can try many mutants at once if each test carries at most one: dgf writes a plan file of "test → mutant id" lines and the switch turns on only the planned mutant for the running test. Packing runs in rounds. First, each mutant gets one test: the quickest test that reaches it, spread so that no test carries many mutants (each mutant already given to a test counts as half a second more), which keeps the packs few. Most mutants that are killed at all are killed by that test, so most never run with the rest. Then each round's survivors get their next untried tests, quickest first, twice as many each round (2, 4, 8, ...), until none survives or none has a test left: a killed mutant's other tests never run, and the slowest tests run only for what the quick ones miss. In each round, mutants are placed first-fit, the most-reached first, into packs of at most 200 tests; only those tests run (for Vitest/Jest, only the test files that hold them). A failing planned test kills its mutant, with two checks in dog-food's worker (C#). The *kill check*: a failed test runs again at once with no mutant, and one that fails again was failed by state the process carries (a static built with an earlier mutant on, a cached value), not by its mutant, so every kill of that request is *polluted*, the worker is retired, and those mutants run again in a fresh process (step 5), where the result is final. After ten retirements of one test project's workers the check is off for it, with a note: its tests are not idempotent. The *activated check*: the switch notes each planned mutant that took effect in its test, and a planned test that passed without its mutant ever taking effect (the mutant sits in a static the process built earlier, in a class fixture's constructor that ran before the test was known, in a memoized value) decided nothing, so the mutant runs again in a fresh process too. A mutant is a *survivor* only once every test that reaches it has run and passed with the mutant in effect; one whose rounds the budget cut short, or whose run could not start, keeps no outcome and is reported as not tested, with the tests that did run. A pack whose run could not start (its run folder could not be cleared, say) sends its mutants to solo runs; a mutant whose solo run cannot start either is reported as not tested with the error, and the rest of the run goes on. Packs run in parallel (`--jobs`, default: cores - 1, so one is left for the rest of the machine), each with its own results folder. `--no-mix` gives every mutant a test run of its own instead.

   A test run counts as hanging, and its mutants as *timeout*, after (startup + the time its tests took without mutants) × `timeout_factor` (1.5) + `timeout_ms` (5000). Each test's time comes from the baseline run (the .NET worker times each test from the end of the one before, so the class fixtures it set up count; the collector and Vitest and Jest report it), and startup is what each test project's run took besides its tests: none in a worker that already ran tests, and a new worker gets twice its warm-up on top. A worker that runs past its limit is stopped, and a new one serves the next run. On Windows the limit is checked against processor time as well: a test run that is past it but has used less processor time than the limit (because the machine is busy, or the run is at `--low-priority`) gets more time, up to ten times the limit, while a run that keeps a processor busy, as an endless loop does, is stopped at the limit. dgf always confirms a timeout before it counts: a mutant whose own run timed out runs once more with four times the time (and at least 30 s more), and only a second timeout makes it *timeout*. On a loaded laptop the tight first limit is often missed by runs that are only slow; without the second run, a mutant no test catches can be reported as caught. Processor time cannot tell a slow run from a stuck one on its own (tests run in parallel, and JIT and GC keep other threads busy), so a run that kept a processor busy gets the second run too; a real endless loop costs one more run and nothing else.

   Node runners have no way to run a failed test again at once, and tests of one file share what they leave behind (a mock's queued value, a global), so a mutant on one test can fail or hide the next. Two checks catch most of that. The switch notes each planned mutant that took effect: a test that failed or passed with its mutant off decided nothing, and that mutant runs alone. And a mutant that survives its packs runs alone before it counts as a survivor. The commonest leak is kept out by packing: a test that queues a mock's next value (`mockRejectedValueOnce`, `mockImplementationOnce` and the like) leaves that value for the next test if it fails first, so it shares a pack with no other mutated test of its file. Other state a failed test leaves behind can still cause a false kill; `--no-mix` gives every mutant a run of its own, which takes longer.

   A run that tests one test at a time (the Microsoft.Testing.Platform worker) gets each mutant's tests quickest first and skips a mutant's other tests once one fails: a failing test kills its mutant whatever the others do.

   **xUnit v3 runs sets of tests.** A request per test is what costs most under Microsoft.Testing.Platform, and xUnit v3 says inside the test process which test is running, so the switch asks it. A plan goes in sets: each mutant's first test in one request, then the next test of each mutant still alive, so a killed mutant's other tests are still skipped. The sandbox's build output sets xUnit to one test at a time. The other frameworks on the platform keep one request per test. A run with one mutant on from the start needs no test name on any framework, so its requests grow as tests pass, and it still stops at the first failure.

   **A run stopped at its time limit keeps what it reported** (Microsoft.Testing.Platform worker). The worker says when each test starts and sends a passed test's result at once. The mutant whose test was running gets a solo run, and mutants whose tests had not started go back in the next round's packs, up to three times.
5. **Solo runs** for what packs cannot decide: mutants reached outside any test (static initialisers, module load), packs that ran over the time limit, and mutants a warm process cannot be trusted on (a polluted kill, a mutant that never took effect). A solo run turns one mutant on for every test that reaches it in a warm worker, with the same two checks; or, when it is reached outside tests or needs a fresh process, in a new worker started with the mutant on, since a warm worker built its statics already. That fresh run takes the tests in order, the tests that reach the mutant quickest first, then the classes its static constructor first ran in, then the rest, a class at a time, and stops at the first failure: one failing test decides it. Test projects whose build output does not hold the mutant's assembly cannot notice it and are left out.
6. **Cache.** One entry per mutant, in `.dgf/mutation-cache/mutants.json` (or `cache_dir`). Entries are keyed by the file's path in the repository, the function's name and the hash of its text, never by branch or folder, so one `cache_dir` can serve every clone and worktree. Results of another dgf version are not reused: a new version may decide mutants differently. An outcome is reused while the function's text and the build settings (project files in the closure, `Directory.Build.*`, `Directory.Packages.props`, `global.json`, `NuGet.config`; for Node, `package.json`, lock files and test-runner configs) are unchanged, and:
   - *killed*: the source files of the tests that killed it are unchanged (dgf finds a test's file from the test adapter, or else from the class that declares the test);
   - *survived*, *no tests*, *timeout*: no file of the chosen test projects (or test files of the package) changed, and the filters are the same, since any new or changed test could kill it;
   - *did not compile*: nothing more.

   The cache also records the test files that reach each mutant. When a branch changes a test file, `--changes` adds the functions whose mutants that file reached last time (reason `tests`); the rules above then decide what is tested again.

   The cache does not notice a change to other production code that makes a killing test miss the mutant; `--no-cache` tests everything again (and saves the new results). Runs that finish at the same time merge their results under a file lock, and the file is replaced in one step, so a reader never sees half of it. Entries unused for 30 days are dropped. `dgf analyze` reads the same cache to fill the MUTATION column in every report format.
7. **Report.** Table, JSON, agent, the mutation-testing-elements report and an HTML page (score, survivors, a bar per function, every mutant with an outcome filter, every `dgf-disable` comment).
8. **Debug log.** Every run, released builds included, writes `dgf-mutate.log` next to its sandbox (`%TEMP%/dgf-mutate/<sandbox>.runs/`; the last progress line names it), and the run before it stays as `dgf-mutate.previous.log`. To see why a run stalled, read `[machine]` (how busy the processors are and how much memory is free, every 10 seconds), `[alive]` (every 5 seconds during a request: which test is running, results so far, threads and queued work items), `[silent]` (a worker that said nothing for 15 seconds, so its process is frozen or starved), a timed-out request's last word, and `[stop]` (a worker that took over a second to stop). One timestamped line per step: how long each phase took, which assembly each test project runs from, each worker's start, every request with its time, processor time, limit and result, the baseline's shards, every pack and solo run, timeouts, the mutants that survived without a run, and each worker's allocations, collections and memory after every request. `baseline/baseline-times.tsv` beside it holds every test's time in the baseline, slowest first, and the log names the slowest classes.

## Why this is fast

- **Few mutants:** functions, not projects; `--changes` usually means tens of mutants, not thousands.
- **Warm test projects (C#):** a test run in dog-food's worker costs its tests, not a new test host.
- **Every core for the baseline:** a test project's tests split across `--jobs` workers, balanced by last run's times.
- **Rounds that double:** a mutant's tests run quickest first, a few more each round, and stop at the first kill.
- **No run for a mutant no test can notice:** a comparison or condition whose value no test changes survives without one, and one that changes only in some tests runs with those.
- **One build** for all mutants, and never more than one sandbox per language.
- **Packing:** with per-test reach, the number of test runs is about *max mutants a single test reaches*, not *number of mutants*: 22 mutants became 11 runs on the small sample.
- **One test first:** a mutant runs with all its tests only when its first test does not kill it.
- **Only reaching tests run** in each pack (C#: by name; Node: their test files). A mutant reached while modules load runs alone with the test files that loaded it, and, if none noticed it, once more with every test: where test files share a process, a module loads under only the first one that needs it. A kill in that run has to hold when only the files that failed run again, since test files in one process can also fail by their order. For these mutants every test of a file runs, so a test that also fails with no mutant (one that depends on the clock, say) does not count as their kill.
- **Test runner kept alive:** Vitest, also the one inside `ng test`, stays alive after the baseline, so a run does not pay for a new start or an Angular build. Each run gets new test processes, which read that run's mutants from a file. A run past its limit loses only those processes, and the next run goes on. Runs of one runner take turns, and each uses `--jobs` test processes. A run of hundreds of mutants starts up to two more runners, within `--jobs`, one per 100 mutants, while 3 GB of memory is free: a runner takes about as long to start as ten test runs. If the runner cannot stay alive (a build that fails, a Vitest too old for it, one that ended), each run starts its own, as Jest always does; the debug log says why under `[warm]`.
- **Only the tests you choose run at all:** filters and excluded test projects apply to the baseline too, which is where unscoped mutation runs spend most of their time.
- **Small, lasting sandbox:** only the projects the tests need are copied, and the build output stays between runs.
- **Cache:** a killed mutant is never run again while its function, its killing tests and the build settings are unchanged.
